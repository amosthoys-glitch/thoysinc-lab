> 환경: Windows Server 2025 DHCP · DC1(주) · DC2(대기) · 단일 사이트
>
> 연재 「노트북 한 대로 AD 홈랩」 7/8 · 작업일 2026-08-22

DHCP를 DC1 한 대에만 두고 여섯 단계를 지나왔습니다. 설계 메모에는 "가장 시급한 이중화"라고 적어 놓고 정작 손대지 않은 항목이었습니다.

## 왜 지금인가 — 시급해서가 아니라 값싸서

DHCP 서버가 죽어도 **즉시 장애가 나지는 않습니다.** 클라이언트는 임대 기간의 50%가 지나야 갱신을 시도하므로, 임대가 8일이면 서버가 몇 시간 꺼져도 기존 단말은 아무 영향이 없습니다. 새로 부팅하거나 새로 접속하는 단말만 주소를 못 받습니다.

그래서 "가장 시급한"은 틀린 말이었고, 정확히는 **"가장 값싸게 얻는 이중화"** 입니다. DC2는 이미 있고, 페일오버는 추가 라이선스도 장비도 필요 없습니다. 설정 몇 줄로 단일 장애점 하나가 사라지니 미룰 이유가 없을 뿐입니다. 우선순위를 정할 때 "얼마나 위험한가"와 "얼마나 싼가"는 다른 축입니다. 섞어 말하면 판단이 흐려집니다.

## 구성

1. **DC2에 DHCP 역할 설치.** FS1을 복제해 만든 DC2에는 DHCP가 들어 있지 않았습니다
2. **AD에 DHCP 서버 인가.** 인가되지 않은 DHCP 서버는 도메인 환경에서 주소를 발급하지 못합니다
3. **페일오버 관계 생성.** 범위(스코프)는 DC2로 자동 복제되므로 따로 만들 필요가 없습니다

```powershell
Add-DhcpServerv4Failover -ComputerName DC1 -PartnerServer DC2 `
    -Name 'DC1-DC2-Failover' -ScopeId 192.168.100.0 `
    -ServerRole Active -ReservePercent 5 `
    -MaxClientLeadTime 01:00:00 -AutoStateTransition $true -StateSwitchInterval 01:00:00
```

```
모드       HotStandby     DC1 = Active / DC2 = Standby
상태       Normal         (양쪽 모두)
예비 비율  5%             통신 두절 시 대기 서버가 쓸 몫
MCLT       1시간
자동 전환  켬 · 60분 후 전체 인계
```

**핫 스탠바이와 부하 분산은 배타적**입니다. 핫 스탠바이는 평소 주 서버가 전부 처리하고 죽으면 대기 서버가 인계합니다. 부하 분산은 두 대가 비율대로 나눕니다. 사이트가 하나이고 서버가 나란히 있으면 핫 스탠바이가 단순하고 추적하기 쉽습니다. "누가 준 주소인가"의 답이 평소엔 하나니까요.

### 막힌 곳 — `Parameter set cannot be resolved`

처음에는 `-LoadBalancePercent`(부하 분산 전용)와 `-ServerRole`·`-ReservePercent`(핫 스탠바이 전용)를 같이 넘겼습니다. 두 방식은 서로 다른 **파라미터 세트**라 섞을 수 없습니다. 오류 메시지가 어느 파라미터가 문제인지 알려 주지 않아서, `Get-Help Add-DhcpServerv4Failover`의 구문 블록이 몇 개인지부터 봐야 합니다. 구문 블록이 여러 개면 그게 세트입니다.

## 전환 시험 — 실제로 꺼 봤다

**시험 전, 임대 데이터베이스 동기화.** 페일오버 관계가 맺어지면 임대 정보가 양쪽에 실시간으로 복제됩니다. 대기 서버가 인계했을 때 이미 나간 주소를 다시 주지 않기 위해서입니다.

```
DC1 임대 4건        DC2 임대 4건
  192.168.100.100     192.168.100.100
  192.168.100.101     192.168.100.101
  192.168.100.102     192.168.100.102
  192.168.100.103     192.168.100.103
완전 일치
```

**DC1 정지 → 클라이언트 재요청.**

```
DC1 DHCPServer 서비스 정지
DC2 상태        Normal → CommunicationInterrupted   (자동 감지)
CL1 에서 ipconfig /release; ipconfig /renew
  받은 IP       192.168.100.102     (같은 주소 유지)
  임대 서버     192.168.100.12      ← DC2 가 인계
```

클라이언트는 아무것도 눈치채지 못했습니다. 같은 주소를 그대로 받았고, 다른 서버가 응답했다는 사실은 `DHCP Server` 값에서만 드러났습니다. DC1 서비스를 다시 켜자 수동 개입 없이 양쪽 모두 Normal로 돌아왔습니다.

## 상태 기계 — 통신 두절과 전체 인계는 다르다

| 상태 | 의미 | 대기 서버가 하는 일 |
|---|---|---|
| Normal | 양쪽 정상 | 발급하지 않음 (주 서버 전담) |
| CommunicationInterrupted | 파트너와 통신 두절 | 예비 비율(5%)만큼만 발급 |
| PartnerDown | 파트너가 죽었다고 판정 | 전체 범위에서 발급 |

왜 곧바로 전체를 인계하지 않을까요. 잠깐 끊긴 것과 정말 죽은 것을 구분하지 않으면, 주 서버가 돌아왔을 때 **같은 주소를 두 서버가 각각 발급했을** 위험이 생깁니다. 그래서 통신이 끊기면 먼저 예비 몫만 쓰고, 설정한 시간(여기서는 60분)이 지나야 전체 인계로 넘어갑니다. MCLT가 그 안전 장치입니다.

급하면 수동으로 PartnerDown으로 바꿀 수 있고, 실무 장애 대응에서 하는 조치가 그것입니다. 다만 **주 서버가 정말 죽었는지 먼저 확인**해야 합니다. 살아 있는데 강제로 전환하면 주소 중복이라는 더 나쁜 문제를 만듭니다.

## 정리

이번 단계에서 얻은 습관은 **"꺼보기"** 입니다. 구성하고 상태가 Normal인 것만 확인했다면 실제로 넘어가는지는 몰랐을 것입니다. 주 서버를 정말 멈추고 클라이언트에서 주소를 다시 받아 본 것이 이 단계의 핵심입니다. 해 본 적 없는 자동 전환은 필요한 순간에 동작하지 않는 경우가 많습니다. 인터넷 회선 이중화도 같은 원칙입니다.

마지막 회는 순서를 조금 거슬러, 이 랩 전체를 VM 3대째 다른 PC로 옮긴 이야기입니다.
